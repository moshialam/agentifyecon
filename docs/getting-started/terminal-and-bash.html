The terminal and bash, for GUI users

If your career has been in Stata, Matlab, or RStudio, this is the missing ten minutes of context that makes Claude Code feel ordinary instead of intimidating.

Most economists I know have spent a career in graphical software: the Stata window with its menus, Matlab’s IDE, RStudio, Excel. None of those require you to think about the terminal. So when Claude Code starts typing things like Rscript analysis.R or git status in a black window, it can feel like a different planet.

It isn’t. The terminal is just the original way to talk to a computer: type a command, hit Return, see the output. There are no menus and no icons — just text in, text out. This page covers the minimum terminal vocabulary you need to (a) follow what Claude Code is doing on your behalf, and (b) type the few commands you’ll actually need yourself.

Tip

You do not need to learn the terminal to use Claude Code. You only need to read what Claude does in it. Once you can read its output, you can work confidently.

What “the terminal” actually is

A terminal is just a window where you type a command and your computer runs it. That’s the whole concept.

  • The window is called a terminal emulator (on a Mac, it’s the app called Terminal; iTerm and Warp are popular alternatives).
  • Inside that window, a small program called a shell is reading what you type and running it. On modern Macs the default shell is zsh. On Linux and on most Windows-WSL setups it’s bash. The two are nearly identical for our purposes; people use the names interchangeably.
  • Each line you type is a command — usually a program name, sometimes followed by arguments (what to run it on) and flags (options starting with - or --).

So when you see Claude Code run:

Rscript --vanilla analysis.R

That’s three pieces: the program (Rscript), a flag (--vanilla, meaning “don’t load my personal R settings”), and the file to run (analysis.R).

How to open a terminal (Mac)

The fastest way:

  1. Press Cmd + Space to open Spotlight.
  2. Type Terminal and hit Return.
  3. A small window with a blinking cursor appears.

You’ll see something like:

yourname@your-mac ~ %

That’s the prompt, telling you it’s ready for a command. Type a command, hit Return.

Note

Windows users: install WSL and open “Ubuntu” from the Start menu. Inside, everything on this page works identically.

Linux users: you already know how to open a terminal.

The seven commands you will see most often

These cover ~90% of what Claude Code does in the terminal and 100% of what you’ll ever need to type yourself.

Command What it does Example
pwd Print working directory — “where am I?” pwd
ls List files in the current directory ls (or ls -la for details)
cd Change directory — “move into this folder” cd ~/Desktop/papers
mkdir Make a new (empty) folder mkdir tables
cat Show a file’s contents in the terminal cat README.md
cp Copy a file cp data.csv data_backup.csv
mv Move or rename a file mv old.do new.do

Two notes:

  • The ~ symbol means “my home directory” — the one with Desktop/, Documents/, etc. So cd ~/Desktop/papers is unambiguous from anywhere.
  • Hit Tab to autocomplete file and folder names. Type cd ~/Des then Tab → it fills in ~/Desktop/. This is the single most useful keypress in the terminal.

What “bash” really is, in one paragraph

A “bash script” (or “shell script”) is just a plain-text file with a list of these commands in it. When you “run” the script, the shell goes through the file line by line and runs each command in order. That’s all. A master.do file is a Stata script. A .bash or .sh file is a shell script. Same idea, different language.

Claude Code can read your shell scripts, write new ones, and run them. It can also string together one-off commands without writing a script. You don’t need to learn shell scripting to use Claude Code — but knowing it exists helps you read what Claude is doing.

What Claude Code actually runs in your terminal

When you watch Claude Code work, you’ll see it call out tools. The most common one is Bash, which means “run this in the terminal”. For econ-research projects, the commands you’ll see most are:

# Inspecting a project
ls
pwd
cat README.md
git status                  # what files have changed since last save
git diff paper.tex          # what specifically changed in paper.tex

# Running your code
Rscript scripts/01-clean.R              # run an R script
stata-mp -b master.do                   # run a Stata .do file in batch mode
python -m statsmodels analysis.py       # run a Python script
matlab -batch "run('main.m')"           # run a Matlab file
julia --project main.jl                 # run a Julia program

# Building a paper
latexmk -pdf paper.tex                  # compile a LaTeX document end-to-end

# Inspecting output
head output/table_3.tex                 # peek at the first lines of a file
wc -l data/clean.csv                    # count lines in a file

You don’t need to memorize any of these. You just need to recognize that when Claude says “I’ll run the master script now” and you see a Bash tool call with stata-mp -b master.do, that’s the same thing you’d do by clicking “Run” in Stata’s window — Claude is just doing it in a way that lets it read the output and decide what to do next.

A quick note on sed — text editing from the command line

sed (“stream editor”) is a small program that edits text without opening a file in an editor. You will see it in inherited scripts; you will occasionally see Claude Code reach for it when doing the same mechanical change across many files at once.

It looks intimidating because the syntax is dense, but 95% of what anyone uses sed for is one pattern: find and replace.

The one pattern you’ll see

sed 's/OLD/NEW/g' file.txt

In English: “in file.txt, substitute NEW for every occurrence of OLD, and print the result.” The s means substitute; the g means globally (every match on each line, not just the first).

By default, sed prints the modified text to the terminal — your file on disk is not changed. To actually save the change back, add -i (“in-place”):

sed -i 's/OLD/NEW/g' file.txt          # Linux / WSL
sed -i '' 's/OLD/NEW/g' file.txt       # macOS (note the empty '')
Warning

Mac vs. Linux foot-gun. macOS uses BSD sed; Linux uses GNU sed. The -i flag works differently on each. On macOS you must follow -i with an empty string '' (the “backup suffix”). On Linux you don’t. This bites everyone the first time. If you’re following a script written on a Linux machine and sed -i complains “extra characters at the end of l command”, that’s the bug.

Examples relevant to econ work

Rename a variable across every .do file in a folder:

sed -i '' 's/wage_resid/wage_residual/g' *.do      # macOS

Strip carriage returns from a file your coauthor sent from Windows (causes mysterious LaTeX errors):

sed -i '' 's/\r$//' paper.tex

Replace a hardcoded path in a script:

sed -i '' 's|/Users/coauthor/Dropbox|/Users/me/Dropbox|g' master.do

Note the | separator instead of / in the last example — sed accepts any character as the separator, and | is much more readable when the pattern itself contains slashes (like a file path).

When Claude uses sed and when it doesn’t

For editing your project files, Claude Code prefers its own Edit tool — it shows you a clean diff per change and is harder to misuse. You’ll mostly see Claude reach for sed when:

  • The same change applies to many files at once (e.g., rename a variable in 30 .do files).
  • The edit is in a file Claude shouldn’t keep “in memory” (a multi-GB log file, for example).
  • A user has explicitly asked it to use the command line.

If you see Claude run sed -i against a file you care about, that change is not going through the diff-review path you’re used to. Verify the result with git diff afterwards, or commit before letting Claude run it so git checkout . is your undo button.

Searching with grep

grep is the search tool. Give it a pattern and one or more files; it prints the matching lines. Read-only — it never changes anything — so it’s safe to type freely.

The basic pattern:

grep "wage_resid" analysis.do

In English: “show me every line in analysis.do that contains wage_resid.”

The flags you’ll actually use:

Flag What it does
-r Recursive — search inside every file in a folder and its subfolders
-n Show line numbers next to each match
-i Case-insensitive
-l List only the filenames that match (not the matching lines)
-v Invert — show lines that don’t match
--include="*.do" Only look in files matching this pattern

In practice, grep -rn is the workhorse — recursive search with line numbers. Once you have it in your fingers, it replaces a lot of “where did I define this variable” cmd-F’ing across files.

Examples relevant to econ work

Find every place a variable is used across a project:

grep -rn "wage_resid" .

Find which .do files reference a particular dataset:

grep -rln "clean_data_v2.dta" --include="*.do" .

Find every TODO or FIXME comment a coauthor left in the code:

grep -rn -E "TODO|FIXME|XXX" .

Check whether a particular paper is cited in your manuscript:

grep -rn "smith2024" paper.tex appendix.tex

List every .bib entry by author surname (rough but fast):

grep "^@" references.bib | head      # entry types
grep "author = " references.bib | head

When Claude uses grep and when it doesn’t

Claude Code has a dedicated Grep tool that’s faster and friendlier than shelling out to grep (it uses ripgrep under the hood). You’ll usually see Claude use that instead. You’ll see actual grep in scripts written by humans, in old replication packages, and occasionally when Claude is piping output through several commands at once.

Either way, the mental model is the same: grep finds; it doesn’t change anything. If you typed it and you don’t like the result, type something else. There’s no recovery to do.

Column work with awk

awk is the tool for column-oriented text — CSV files, log files, TSVs, anything where you care about “the third whitespace-separated field on each line.” It’s a tiny programming language in disguise. You will use 5% of it; that 5% is genuinely useful.

By default, awk splits each line on whitespace and exposes the columns as $1, $2, $3, … with $0 being the whole line.

The basic pattern:

awk '{print $3}' file.txt          # print the 3rd column of every line

For CSVs (or any non-whitespace separator) use -F:

awk -F',' '{print $1, $4}' data.csv      # 1st and 4th comma-separated columns

The four patterns that cover most use

# 1. Print specific columns
awk '{print $1, $5}' file.txt

# 2. Filter rows by a column condition
awk '$3 > 100' data.csv               # rows where column 3 > 100

# 3. Sum a column
awk '{sum += $2} END {print sum}' data.csv

# 4. Count rows matching a condition
awk '$3 == "treatment"' data.csv | wc -l

The END {...} block runs once after all lines are read — that’s how you accumulate totals or counts. There’s also a BEGIN {...} block that runs before any input.

Examples relevant to econ work

Quickly peek at one column of a 10 GB CSV without loading it into R or Stata:

awk -F',' '{print $7}' huge_admin_data.csv | head

Count distinct values in a column (rough but fast):

awk -F',' '{print $3}' data.csv | sort | uniq -c | sort -rn

Sanity-check a sum from a Stata table against the underlying data:

awk -F',' 'NR>1 {sum += $4} END {print "Mean wage:", sum/(NR-1)}' wages.csv

(The NR>1 skips the header row; NR is awk’s built-in row counter.)

Extract just the variable names from a Stata describe log:

awk '/^[a-z]/ {print $1}' describe.log

Honest framing

awk is rarely the right tool when you have R, Python, or Stata already loaded. Its real niche is the in-between moment: you want a quick number from a file, and starting a full session in your stats language is overkill. For that — and for one-liners that Claude Code writes for you in a script — it’s hard to beat.

Like grep, plain awk is read-only; it prints to the terminal. It only modifies a file if you explicitly redirect output (> newfile.txt) or chain it through sed -i.

Other text tools you’ll see in passing

You don’t need to learn these, but recognize them when they go by:

  • tr 'A' 'B' — character-by-character translation. Useful for uppercasing, stripping punctuation, normalizing line endings.
  • cut -f3 -d',' — extract a column from a delimited file. Like a one-trick awk for the “I just want column 3” case.
  • sort and uniq — sort lines, then collapse duplicates. The sort | uniq -c | sort -rn pattern (used in the awk example above) is the canonical “frequency table from a column” idiom.
  • xargs — take a list of things from stdin and run a command on each. Common with find ... | xargs grep ....

For all of these, the rule is the same: read what they do; let Claude write them; verify the output.

Safety: commands to never type without thinking

Most terminal commands are harmless. A few are not. Treat the following the way you’d treat a power tool — fine when you mean to use it, dangerous when you don’t:

Warning

rm -rf <folder> — recursively, forcefully deletes a folder and everything inside it. No trash, no undo. Especially dangerous near ~, /, or * wildcards. Claude Code will prompt before doing this; don’t blanket-allow it.

sudo <anything> — runs the command as the system administrator. Almost never necessary for econ-research workflows. If something is asking you to sudo, slow down and figure out why. (The most common honest reason is sudo apt install on Linux to install software.)

chmod 777 <file> — makes a file readable, writable, and executable by everyone. The internet is full of “fix it with chmod 777” advice that “fixes” the problem by making your machine less safe. Don’t.

curl ... | bash or wget ... | sh — downloads code from the internet and immediately runs it without you reading it. Even from “trusted” sources, this is risky. Download first, read, then run.

git push --force to a shared branch — overwrites your coauthors’ work with no warning. If you’re sharing a repo, never force-push without talking to your coauthors first.

sed -i ... (or any in-place edit) without a git commit first — silently rewrites the file with no diff and no undo. The fix is a one-second habit: git add -A && git commit -m "before sed" before any sed -i you didn’t write yourself. See the sed section above.

The pattern: be suspicious whenever a command is destructive, privileged, or fetched from the internet and run sight-unseen. For everything else, the worst case is usually “type it again”.

When to let Claude drive vs. type yourself

A pragmatic rule of thumb:

  • Reading commands (ls, pwd, cat, git status, git diff) — always fine for Claude to run automatically. They can’t break anything.
  • Building / running code (Rscript, stata-mp -b, latexmk) — fine for Claude to run, but watch for the failure mode where the script has side effects (writes files, sends an email, etc.). The first time you run a script under Claude, watch what it does.
  • Edits to your project files — Claude does these via its Edit and Write tools, which show you a diff. Read the diff. Always.
  • Destructive shell commands (rm, mv over an existing file, git checkout that discards work) — Claude prompts. Don’t blanket-allow.
  • git push, git push --force, deploying anything — type yourself, always. These are visible to other people. Make the decision consciously.

A five-minute exercise

Open Terminal. Type each of these in order; press Return after each:

pwd
cd ~/Desktop
ls
mkdir terminal-test
cd terminal-test
echo "I survived the terminal" > note.txt
cat note.txt
cd ..
ls

You just: checked where you were, moved to your Desktop, listed the contents, made a folder, moved into it, created a text file in it, read the file, went back up one level, and listed the contents again. That is the entire terminal vocabulary you need to start using Claude Code.

When you’re done, you can clean up:

rm terminal-test/note.txt
rmdir terminal-test

(Note: rmdir only removes empty folders, so it’s safer than rm -rf.)
